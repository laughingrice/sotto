# Validation tools

## Exact voice lengths: validate_score.py

Requires Python 3 and LilyPond 2.26 or later (tested with 2.26). The input `.ly` is executable LilyPond/Guile; use it only for trusted transcription files, not as a sandbox for untrusted code. It can include ordinary score blocks. The wrapper and compilation outputs go to a temporary build directory (or `--build-dir`), not beside the input.

Keep the canonical score as continuous instrument blocks. The existing validator consumes a **separate generated audit `.ly`**, with one variable per source measure and a JSON manifest. Store the audit, manifest, generation script and reports under `review/`; do not make the user edit per-bar variables.

Generate the audit from the current canonical music, not a second manually maintained transcription. Record the source hash and audit hash together. Extraction must preserve inherited durations, relative-pitch context, tuplets and print/MIDI alternatives; splitting raw text at `|` and parsing each bar afresh is unsafe in the general case. For simple absolute-pitch music with explicit durations, a narrowly scoped extractor can reject unsupported constructs rather than guess. For relative or inherited notation, resolve it through LilyPond or carry the necessary context explicitly. Check audit-to-score correspondence using compiled events and, for a source-only refactor, compare engraving and MIDI with the pre-refactor outputs. Hash-register the canonical score, generated audit and generator in the review record. A passing audit alone does not prove that the canonical score matches it.

The generated manifest has this form:

```json
{
  "schema_version": 1,
  "tags": ["print", "midi"],
  "measures": [
    {
      "number": 5,
      "variable": "mE",
      "meter": "3/4",
      "voices": {"melody": "music", "bass": "music", "barres": "annotation"}
    }
  ]
}
```

Zero-duration unnamed context settings generated by commands such as `\voiceOne` are controls, not separate voices. Anonymous counterpoint inside an outer named voice is still rejected.

Variables contain named `\context Voice = "..."` or `\new Voice = "..."` blocks. Each listed voice appears once in the measure variable. Combine fragments of the same voice before auditing; the helper intentionally rejects duplicate context fragments rather than accidentally checking each as a whole bar. Avoid duration-bearing notes/rests/skips outside these blocks. For a genuinely monophonic measure, declare one musical voice; do not invent dummy counterpoint. Annotation voices contain only skips and control/marking events and must also fill the bar.

For pickups use `"expected_duration": "1/8", "exception_reason": "Source pickup"`. For a free coda, use `"unmetered": true`, a positive exact `expected_duration`, and `exception_reason`. Meter/exception values are assertions made by the transcriber; verify them against the source. Do not insert `\cadenzaOn` just to silence a duration error.

```sh
python3 scripts/validate_score.py review/audit.ly --manifest review/measures.json \
  --report review/durations.json --build-dir /tmp/score-audit
```

The Scheme helper resolves music via LilyPond, filters print/MIDI tags independently, then checks the whole measure and **each** musical/annotation voice with exact rational arithmetic. This catches errors masked by the longest simultaneous voice. Relative pitch entry, tuplets, duration inheritance and grace structures are handled by LilyPond, not a regex duration parser. Set the manifest's tags to the variants actually used by your score (`print`/`midi` in the example). A no-tag score can be checked under either symbol; untagged music remains.

Exit 0 requires every manifest check to complete and pass, plus no compiler warnings/errors/programming errors. Exit 1 includes diagnostics in JSON; a LilyPond exit code of 0 alone is insufficient. `--timeout` defaults to 120 seconds. `--lilypond` accepts an alternate executable. Missing tools, malformed manifests and unresolved variables fail rather than returning an empty success.

**Limits:** This proves structural lengths for the variables in the manifest, not exhaustive source coverage, pitch accuracy, correct ties/slurs, layout, or navigation. Ensure every source measure is represented and separately compile/render the actual score. An incorrect manifest can validate incorrect music. Use the visual review gate.

## Comparison images: compare_pages.py

Requires Poppler and Pillow (the desktop bundled Python is suitable). Provide a config:

```json
{
  "title": "Measures 5-8",
  "original": {"pdf": "original.pdf", "page": 1,
               "crops": [[46.8, 234, 529.2, 88.2], [46.8, 342, 122.8, 79.2]]},
  "corrected": {"pdf": "checked.pdf", "page": 1, "trim_white": true},
  "uncertainties": []
}
```

```sh
python3 scripts/compare_pages.py comparison.json --output review/comparison.png
```

Paths are relative to the config file. Crop coordinates are **PDF points from the top-left**, not screen pixels or PDF bottom-left coordinates. Omit `crops` to render the entire page. Multiple source crops are stacked so a group spanning systems remains together. `trim_white` removes only exterior white margins; it does not identify measures. The renderer rejects out-of-page crops and labels the columns. The `.evidence.json` records source page/crop coordinates, input hashes and uncertainty entries. Do not claim automatic musical alignment or optical validation. Open the image and inspect it at a useful zoom before delivery. Show the actual image, not just a link to an uninspected file.

## Verification records: validate_review.py

The full example is `assets/capricho-05-08/review.json`. It records:

- `schema_version: 1`, explicit `group`, `uncertainties: []` or structured entries.
- `artifacts` containing original, LilyPond, rendered, comparison and comparison-evidence paths/hashes, relative to the review JSON. Add MIDI or other evidence when relevant.
- A measure record for each member of `group`, with `assistant_checked` aspects and `assistant_review_complete`.
- `user_verified` evidence events with `measure_numbers`, `aspects`, `extent` (`detail` or `full_measure`), exact free-text `scope`, `date` and supporting user statement. `full_measure_user_verified` remains false unless the user explicitly approved the full measure. Full-measure events must enumerate all five core aspects and cannot coexist with an unresolved reading for that measure.

The five core aspects are `pitches`, `durations`, `accidentals`, `ties`, `voices`. “No ties in this measure” can count as checked; it is not evidence the user verified ties. Other aspect names: `slurs`, `slides`, `fingerings`, `strings`, `barres`, `layout`, `navigation`, `midi`.

An uncertainty entry has `measure`, `aspect`, `question`; it can also retain alternatives and evidence. Machine validation requires an explicit list, not an omitted field. Preserve open readings in the final response rather than hiding them in JSON alone.

```sh
python3 scripts/validate_review.py review.json --report review/evidence-check.json
```

The checker detects missing/changed artifact hashes, missing comparison evidence, inconsistent group membership, misassigned measure confirmations and unsupported escalation from pitch-only to full approval. It links the comparison evidence JSON to the exact original/rendered PDF and image hashes. It does **not** authenticate a quote, interpret its natural-language scope, or make approval decisions. A falsely labeled evidence event remains false even if it passes a schema check. Record the actual user's words; never generate evidence to make the checker pass. After edits, hashes becoming stale means the record no longer describes those exact artifacts; re-review affected aspects before refreshing them. A purely presentational edit need not revoke a genuine pitch confirmation, but must not imply approval of new geometry.

## Regression suite

```sh
python3 -m unittest discover -s scripts/tests -v
```

Tests use real LilyPond to check malformed/implicit voices, masked short voices, tuplets/graces, print/MIDI mismatch, short annotation layers, warning-only builds and explicit pickup exceptions. Review tests verify scoped approval and stale evidence. Comparison tests also exercise real PDF crops and hashes when Pillow/Poppler are available. Tests skip the relevant cases when tools are unavailable; do not call the suite fully passed if they were skipped.

### Include dependencies

Register every local `.ly`/`.ily` dependency as an additional artifact with path/hash. The review checker follows literal `\include "file.ily"` directives recursively, outside comments and strings, and rejects an unhashed include. Nonliteral includes are unsupported for automatic review integrity: make them literal, or document a separate manual dependency audit without claiming this checker covers them. Built-in includes that cannot be resolved locally must be named in `system_includes` with a reason including the LilyPond version. Local files cannot be exempted as system libraries. Other Scheme file reads/configuration are not discovered; record them explicitly as artifacts and review dependencies manually.
